[Better Stack](/ja/articles/better-stack)と[Sentry](/ja/articles/sentry)は、出発点が違う。Better Stackは、稼働監視のBetter Uptimeとログ管理のLogtailという2つの製品を1つに統合して生まれ（公式プレスリリース）、エラー追跡はその上に加わった。Sentryはエラー追跡から始まり、トレースやログ、稼働監視を後から加えた。それでも2社は今、同じ場所で重なっている。アプリに組み込むSentry SDKだ。この記事は、両社の公式の料金ページとドキュメントを2026年11月2日に読み、書かれている数字と条件をそのまま並べる。当サイトは両サービスを契約して使い比べたのではなく、公開されている料金表とドキュメントを突き合わせている。料金は改定されるので、申し込む前に必ず公式ページを確認してほしい。

## 何が重なり、何が重ならないか

:::fact
Better Stackの公式ドキュメント（2026-11-02閲覧）は、自社のエラー追跡を「AI-native error tracking built on Better Stack」と呼び、「Sentry SDK-compatible at 1/6th the price」と書く。既存のSentry SDKのまま「データをBetter Stackに送るだけ」でよく、JavaScript・Python・Go・Ruby・Java・.NET・PHPなど100以上のプラットフォームでエラーを追えるという。SentryのJavaScript SDK（sentry-javascript）のLICENSEはMITで、Better Stackのこの使い方を妨げる条件はない。Sentryのトップページは、エラー・ログ・リプレイ・スパン・プロファイル・メトリクスを同じトレースでつなぐと書き、AIのSeerとMCPサーバーを製品として並べる。Better Stackのトップページは、eBPFによるサービスマップ（トレース）、ログ、OpenTelemetryのトレース、インフラ監視、エラー追跡、インシデント管理、ステータスページ、AI SRE、稼働監視、セッションリプレイを含むリアルユーザーモニタリングを並べる。
:::

:::fact
両社の公式ページ（いずれも2026-11-02閲覧）から、製品の有無を当サイトが並べ直した。「記載なし」は、当サイトが読んだページで確認できなかったという意味で、提供していないと断定するものではない。

| 機能 | Better Stack | Sentry |
| --- | --- | --- |
| エラー追跡 | あり（Sentry SDK互換） | あり（自社SDK） |
| トレース | あり（OpenTelemetry・eBPF） | あり（スパン課金） |
| ログ | あり | あり |
| セッションリプレイ | あり | あり |
| 稼働監視 | あり | あり |
| Cron・ハートビート監視 | あり（料金表の監視とハートビート） | あり（Cron監視） |
| プロファイリング | 記載なし | あり（PAYGのみ） |
| オンコール（電話・SMSでの呼び出し） | あり（Responderに含まれる） | 料金ページに記載なし |
| ステータスページ | あり（無料枠に1つ） | 料金ページに記載なし |
| セルフホスト | 料金ページに記載なし（ログ・トレース・メトリクスのカスタムクラスタはEnterprise） | あり（FSLの下で社内利用は可） |
| AIによる修正の提案 | AI SRE、エージェント向けのプロンプト、MCPサーバー | Seer（原因分析・修正のプルリクエスト・コードレビュー）、MCPサーバー |
:::

:::pull
入口のSDKは同じでも、Better Stackは「エラーを当番の電話まで運ぶ」側に、Sentryは「エラーをコードの修正まで運ぶ」側に厚い。
:::

## エラー監視の料金を並べる

:::fact
両社の料金ページとSentryの料金ドキュメント（いずれも2026-11-02閲覧）から、エラー監視に関わる行を並べた。価格はすべて米ドル。Sentryは売上税を含まない表示で、EUと英国ではVAT番号などを出さない注文にVATがかかると書く。

| 項目 | Better Stack | Sentry |
| --- | --- | --- |
| 無料枠のエラー | 月10万件 | Developerプランで月5,000件（利用者1人） |
| 有料の基本料 | テレメトリを見るだけのメンバーは月0ドル。当番のResponderは月34ドル（年払いで月29ドル） | Team月29ドル（年払いで月26ドル）、Business月89ドル（年払いで月80ドル）。Team以上は利用者無制限 |
| 有料プランに含まれるエラー | 10万件 | 5万件 |
| 追加のエラー1件 | 欧州0.000050ドル、米国0.000075ドル、シンガポール0.000175ドル | Team PAYG：5万〜10万件0.0003625ドル、50万〜1,000万件0.0001875ドル、2,000万件超0.00015ドル（予約ならそれぞれ0.00029・0.00015・0.00012ドル）。Business PAYGの2,000万件超は0.0003ドル |
| エラーの保持・さかのぼれる期間 | 90日 | Developer 30日、Team・Business 最大90日 |
| セッションリプレイ | 5,000件込み、追加1件は欧州0.00150ドル・米国0.00225ドル | 50件込み、Team PAYGで50〜5,000件が1件0.00375ドル |
| ログ | 1GBあたり欧州0.10ドル・米国0.15ドル（バンドルは30日保持） | 5GB込み、追加は1GBあたり0.50ドル（PAYGのみ） |
| 稼働監視 | 無料枠で監視とハートビート10件 | 1件込み、追加1件1.00ドル（PAYGのみ） |
| 上限に達したとき | 料金ページで確認できなかった | 予約量とPAYG予算を使い切ったデータは破棄され、課金されない |
:::

:::fact
Better Stackのエラー追跡のページは、1億件の例外を90日保存する想定で、月額の概算をBetter Stack 5,000ドル、Datadogのエラー追跡18,000ドル、Sentry 30,000ドルとし、「最大83%の費用削減」とうたう。脚注によれば、1件あたりの単価はSentryが0.0003000ドル、Datadogが0.00018ドル、Better Stackが0.000050ドルで、欧州のデータ保管とオンデマンドの料金を前提にしている。Sentryの料金ドキュメントでは、0.0003ドルはBusinessプランのPAYGの2,000万件超の単価で、Teamプランの同じ帯のPAYGは0.00015ドル、予約なら0.00012ドルだ。
:::

:::guess
単価だけを比べると、大量のエラーではBetter Stackのほうが安く見える。Teamプランの2,000万件超の帯で比べても、SentryのPAYG 0.00015ドルに対してBetter Stackの欧州は0.00005ドルで3分の1、米国の0.000075ドルでも半分だ。ただしBetter Stackの「6分の1」は、SentryのBusinessプランのPAYG単価を相手にした数字で、Teamプランや予約量を使えば差はそこまで開かないとみられる。逆に、月のエラーが数万件の小さなサービスでは、Better Stackの無料枠10万件に収まる一方、Sentryの無料枠は5,000件で、利用者も1人に限られる。小さく始めるほどBetter Stackの無料枠の広さが効き、量が増えるほどSentryの帯ごとの値下がりと予約割引が差を縮める、という形と考えられる。Sentryの帯の単価が累進で適用されるのか、全量に1つの単価がかかるのかは、当サイトが読んだ範囲のドキュメントには書かれていなかったため、総額の試算はしていない。
:::

## データの置き場所とセルフホスト

:::fact
Better Stackのセキュリティページ（2026-11-02閲覧）によれば、データは既定でEUリージョンのGDPR準拠・DIN ISO/IEC 27001認証のデータセンターに保管され、独自のデータ保管場所はEnterpriseのアカウント向け。SOC 2 Type 2に準拠し、HIPAAには「現在は準拠していない」と明記する。料金ページでは、エラー・リプレイ・ログの単価が欧州・米国・シンガポールの地域ごとに分かれている。Sentryのデータ保管場所のドキュメントによれば、米国（アイオワ）かEU（フランクフルト）を選べ、一度選ぶと変えられない。選んだ地域に置かれるのはエラー・スパン・ログ・リプレイなどで、ユーザーアカウント、組織の設定、監査ログ、Cronのチェックイン、DSNキーなどは常に米国に置かれる。
:::

:::fact
Sentryは、サーバーのソースをFunctional Source License（FSL）で公開し、セルフホスト版を案内している。公式の開発者向けドキュメントによれば、最低要件は4コア・RAM 16GB（加えてスワップ16GB）・空きディスク20GBで、推奨はRAM 32GB。保証や専任のサポートはなく、Seerなどのクローズドソースの機能、スパイク保護、データ保管場所の選択はSaaSにしかない。FSLの下で社内を含めどこにでも導入できるが、セルフホストしたSentryを売ることや、FSLのコードで直接競合することは禁じられ、2年後にApache 2.0になる。Better Stackの料金ページは、ログ・トレース・メトリクスの「カスタムクラスタのデプロイ」と「カスタムVPCのデプロイ」をEnterpriseの項目として挙げるが、利用者が自分で動かすセルフホスト版の記載は確認できなかった。
:::

:::guess
データを自分の設備から出せない組織や、通信が閉じた環境でエラーを集めたい場合、選択肢になるのは実質的にSentryのセルフホストだとみられる。ただし、RAM 16GBからの構成を自分で運用し、AI機能をあきらめる前提になる。EUにデータを置きたいだけなら、Better Stackは既定がEU、SentryもEUを選べるので、どちらでも条件は満たせると考えられる。Sentryではアカウントや監査ログが常に米国に置かれる点は、社内の審査で確認が要る項目になりそうだ。
:::

## エラーのあとに何が起きるか

:::fact
Better Stackの料金ページによれば、Responder（「Incidents + Telemetry」）には当番のスケジュールが含まれ、オンコールとインシデント管理の欄に「電話の呼び出し無制限」「SMS無制限」とある。ステータスページは無料枠に1つ含まれる。エラー追跡のページは、LinearやJiraへのチケット作成、オンコール担当へのエスカレーション、SlackとMicrosoft Teamsでの確認・解決の操作を挙げ、AI SREについては「承認なしに自動で操作することはない」と書く。Sentryのトップページによれば、Seerはログ・コミット・トレース・スタックトレースから「どこで」だけでなく「なぜ」失敗したかを説明し、マージできる修正パッチを作り、プルリクエストをエラーと性能の履歴と照らして退行を出荷前に見つける。料金ドキュメントによれば、Seerはアクティブなコントリビューター（Seerを有効にしたリポジトリに月2件以上のプルリクエストを出した人）1人あたり月40ドルで、PAYG予算とは別に請求される。
:::

:::guess
エラーが起きたあとの流れで、2社の重心ははっきり分かれているとみられる。Better Stackは、エラーをインシデントに上げ、当番に電話をかけ、ステータスページで利用者に知らせるところまでを1社で持つ。夜中に起こされる人が決まっている運用チームには、この一続きが価値になる。Sentryは、エラーを原因のコミットと結び付け、AIに修正のプルリクエストを書かせ、レビューで次の退行を止めるところに厚い。エラーを「直す」開発者の机の上に価値を置いている。どちらの流れが自分たちの痛みに近いかで、選び方は変わると考えられる。
:::

## どんなチームにどちらが合いやすいか

ここからは、上の料金表と条件を当サイトが読んだうえでの整理だ。優劣を付けるものではなく、チームの形ごとに、公式の料金表のどの行が効いてくるかを示す。

:::guess
- 個人開発や小さなSaaSで、エラーと稼働監視とステータスページをまとめて無料で始めたい場合は、Better Stackの無料枠（エラー月10万件・監視10件・ステータスページ1つ）が当てはまりやすいとみられる。Sentryの無料枠は月5,000件で利用者1人なので、2人目が加わった時点でTeamの月29ドルが必要になる。
- エラーの量が多く、単価が総額を決めるサービスでは、Better Stackの欧州0.00005ドルという単価が効いてくる。ただしSentryも予約量と帯ごとの値下がりがあるので、実際の月間件数を両社の料金表に当てて比べるのが確実だ。
- すでにSentry SDKを入れているチームは、Better Stackのドキュメントどおりなら計装コードを変えずに送り先を試せる。ただし、Sentry SDKのどの機能（トレース・リプレイ・プロファイリングなど）がBetter Stack側でどこまで扱えるかは、当サイトが読んだページには詳しく書かれていなかった。移行前に、自分たちが使っている機能ごとに確かめる必要がある。
- iOSやAndroid、ゲームのネイティブなクラッシュを扱うチーム、エラーから修正のプルリクエストまでをAIに任せたいチームは、Sentryの設計が合いやすいとみられる。シンボル化のSymbolicatorやSeerは、Sentry自身の製品として作り込まれている。
- データを外部に出せず、自前の設備で動かす必要がある組織では、Sentryのセルフホストが現実的な選択肢になると考えられる。FSLは社内利用を明示的に認めている。
- 当番の呼び出しとステータスページまでを1つの請求書にまとめたい運用チームは、Better Stackの料金表の形（見るだけのメンバーは無料、当番だけがResponderとして払う）が合いやすいと推測される。Sentryを使いながら、呼び出しは別の製品に任せるという組み合わせも考えられる。
:::

## なぜ同じSDKを受けるのか

:::guess
Better StackがSentry SDKを受けるのは、乗り換えの最大の壁である「計装のやり直し」を消すためだとみられる。トレースやログでOpenTelemetryという業界標準を受けるのと同じ発想で、エラーの世界では、Sentry SDKが事実上の標準の位置にあると判断したのだと推測される。Sentryの側から見ると、SDKをMITで公開している以上、これは止められないし、止めないことを選んだとも読める。Sentryはサーバーのコードにだけ「競合する利用」の禁止をかけ、SDKは誰でも使えるように残している。SDKが他社にも受けられるほど、開発者が最初に入れるのはSentry SDKになり、その標準の持ち主であることがSentryの強みになる、という計算も成り立つ。

結果として、選ぶ側は有利な立場にいる。同じ計装のまま送り先を比べられ、合わなければ戻せる。比べるべきなのは、エラー1件の単価だけでなく、エラーのあとにどの仕事を1社に任せたいかだ。
:::

Better StackとSentryは、同じSDKから入ってくるエラーを、別々の出口へ運んでいる。Better Stackはインシデントと当番の電話とステータスページへ、Sentryは原因のコミットと修正のプルリクエストへ。申し込む前に見るべきなのは、月にどれだけのエラーが出るか、そのエラーを最初に受け取るのは運用の当番か、コードを直す開発者か、そしてデータをどこに置く必要があるかだ。その答えが決まれば、2つの料金表のどの行を読めばよいかはおのずと決まる。
